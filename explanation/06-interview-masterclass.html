Your 30-second opening

“Thesis-Ready is an AI-assisted journal-formatting system. A user uploads a PDF, DOCX, or text manuscript, chooses a journal, receives a pre-format compliance check, and starts an asynchronous formatting job. FastAPI extracts the document and runs three focused AI stages—Parse, Transform, and Validate—alongside deterministic rule checks. It generates a DOCX, reopens that output to verify key formatting facts, and returns an explainable report. For unfamiliar journals, discovery finds candidate guideline sources but requires approval before their rules can be used.”

Your 90-second architecture walkthrough

  1. Frontend: React with Vite owns the upload screen, journal selection, progress state, and results screen. It calls backend APIs with multipart form data for files and JSON for discovery actions.
  2. API layer: FastAPI validates input, extracts PDF/DOCX/TXT content, creates a document ID, and exposes the workflow through routes such as /upload, /score/pre, /format, and status/result routes.
  3. Async job: formatting can take longer than a normal request because it extracts a document, calls an LLM, writes a DOCX, and validates it. The API returns a job ID and the frontend polls for progress.
  4. Reasoning pipeline: the Parse task finds structure, Transform proposes formatting-aware changes, and Validate assesses the output against the chosen rules.
  5. Trust layer: deterministic checks calculate measurable items such as headings, references, fonts, and spacing. A verified-compliance score is separate from the model’s assessment.
  6. Output layer: DOCX generation produces an artifact. A post-format verifier reopens it, checks required facts, and makes at most one safe font-normalization repair.

Questions interviewers are likely to ask

QuestionStrong answer
Is this truly multi-agent?It is a bounded multi-stage agent workflow, not an autonomous system. Parse, Transform, and Validate have separate responsibilities and artifacts. Tool calls and deterministic validation constrain the model. I would not claim open-ended autonomy because the workflow is orchestrated and intentional.
Why not use one LLM prompt?One prompt mixes extraction, interpretation, transformation, and validation. Separating stages makes failures easier to locate, lets us inspect intermediate outputs, and gives deterministic code control over measurable requirements.
Why use deterministic checks when an LLM can score?A model can interpret ambiguous writing guidance, but font size, heading presence, margins, and reference patterns should be measured reproducibly. The verified score exposes what code actually checked and what remains unverified.
How do you limit hallucinations?Rules are structured JSON, discovery sources are ranked and shown to the user, unknown-journal rules require approval, schema validation rejects malformed rules, and the generated DOCX is verified after creation. The model is not the sole source of truth.
Why is discovery failing sometimes?Discovery has external dependencies: web search, source pages, and Gemini extraction. I tested it end to end: search and fetching worked, while a suspended Gemini API credential caused extraction failure. The application now returns a clear configuration error. In production I would monitor each stage separately and provide graceful fallback.
Why asynchronous processing?Document extraction, LLM calls, and DOCX generation can exceed normal request latency. The system starts a job, returns its ID, and the client polls status. That keeps the browser responsive and provides progress feedback.
What happens if the job fails midway?The current job store records an error and the client displays it. The production design would use a durable queue, persisted job state, idempotency keys, retries only for safe transient failures, and a dead-letter queue for investigation.
Why FastAPI?Python fits the AI and document-processing ecosystem. FastAPI gives typed request handling, validation, async-friendly endpoints, and automatic OpenAPI documentation with little boilerplate.
Why React and Vite?React fits a stateful workflow with clear components for upload, journal discovery, progress, and results. Vite keeps local development and production builds fast. If the product needed SSR, SEO, or backend-for-frontend capabilities, I would evaluate Next.js.
Where is data stored?Today, uploaded documents and output artifacts are local files, while document and job state is in memory. That is appropriate for a prototype but is not horizontally scalable or durable.
How would PostgreSQL fit?I would store users, documents, jobs, rule-set versions, approvals, audit events, and artifact metadata in PostgreSQL. Those entities have relationships and consistency requirements, so transactions, constraints, indexes, and joins are valuable.
Why not MongoDB?MongoDB can work well for flexible raw extraction output. Here, approval history and relationships between a job, document, rule set, user, and output are central. PostgreSQL is the better default; JSONB can still store flexible LLM artifacts.
How would you secure it?Authenticate users, authorize access per document and rule set, place files in private object storage, use signed download URLs, encrypt data at rest, set retention policies, redact logs, scan uploads, limit file size and type, and isolate document conversion. I would also restrict discovery URLs to prevent SSRF.

How to answer “how would you improve it?”

Answer in priority order, linking each change to a real current limitation:

  1. Reliability: replace in-memory jobs with a durable queue and persistent job table. Trigger: multiple workers, restarts, or long-running jobs.
  2. Storage: move local uploads and generated DOCX files to object storage. Trigger: deployment beyond one machine.
  3. Security: add login, role-based approval, private artifacts, retention controls, and audit logs. Trigger: real manuscript data or team use.
  4. Quality: create golden papers and journal-rule fixtures, then measure extraction accuracy, validator coverage, repair success, and false positives.
  5. Discovery: snapshot sources, track freshness, review low-confidence rules, and support multiple evidence sources rather than trusting a single page.
  6. Scale: cache immutable approved rule sets, rate-limit LLM work, add per-user quotas, and monitor latency, failure rate, cost, and queue depth.

System-design answer template

1. Clarify

Ask for users, expected volume, latency target, correctness bar, privacy requirements, and whether a human must approve output.

2. Contract

State inputs, outputs, error codes, idempotency, authorization, and success metrics.

3. Data model

Name entities and lifecycle: document, job, rule set, approval, artifact, audit event.

4. Hot path

Client → API → persisted job → queue → worker → artifact → result.

5. Failure design

Time-outs, retry policy, duplicate messages, partial artifacts, cancellation, cleanup, and alerting.

6. Trade-off

Say what is deliberately simple today and the concrete condition that triggers the next design.

Demo script for a live interview

  1. Start with the user problem: journal formatting is slow, inconsistent, and hard to verify.
  2. Upload a sample document and point out the document ID returned by the API.
  3. Choose a built-in journal and show the pre-format score.
  4. Explain that Format returns a job ID, then show progress polling rather than blocking the browser.
  5. Open the result: before/after score, verified compliance, remaining unverified items, and DOCX verification.
  6. Show the unknown-journal discovery screen. Explain that approval is required before discovered rules become active.
  7. Close with one real limitation and your next production milestone. This signals engineering judgment.

Things to avoid saying

  • Do not say PostgreSQL, queues, cloud storage, or authentication are already implemented if they are future work.
  • Do not call the model “always accurate.” Explain verification, confidence, and review instead.
  • Do not say the system automatically knows every journal format. Unknown journals depend on available guidelines and an active external AI provider.
  • Do not hide the Gemini discovery dependency failure. Explain the diagnosis and the graceful error path.

Five questions to ask the interviewer

“What is the cost of a wrong result in this domain?” “Would a reviewer approve changes, or must the system be fully automated?” “What traffic and latency should I design for?” “How sensitive is the uploaded data?” “Which metric defines success: completion rate, turnaround time, or formatting accuracy?”
