60-second walkthrough

“A researcher uploads a PDF or DOCX and selects a journal or custom guideline. Our React web app or Word add-in calls FastAPI. The API validates and extracts the document, resolves one normalized rule set, and starts a background job. A staged CrewAI/Gemini pipeline parses structure, transforms it against the rules and validates the result. Deterministic Python checks cover measurable compliance facts. Finally we generate a DOCX, return a compliance report, and let the user preview, download or apply it in Word. The current implementation uses local/in-memory storage for speed; a production version would add PostgreSQL, object storage and durable workers.”

Core defense questions

Why AI agents instead of one prompt?

One prompt mixes extraction, policy interpretation, transformation and validation, making failure diagnosis difficult. Staging narrows each model responsibility, makes intermediate artifacts inspectable, and lets exact code handle rules that should not be guessed.

How do you prevent hallucinated formatting?

We do not rely on the model as the only authority: built-in rules are structured JSON; custom rules are normalized and schema-validated; deterministic checks override measurable parts of the report; and generated output is available for user review. Next: confidence thresholds, golden-document tests and human approval for sensitive changes.

Why is formatting asynchronous?

PDF/DOCX extraction, several model calls and file generation can take far longer than a normal web request. The API returns a job ID immediately and the client polls its state, which avoids holding a request open and lets progress be shown.

Why not put every rule in prompts?

JSON rules are versionable, testable and reusable across clients. Prompt text is then an interpreter of an explicit policy, not the only place where business behavior exists.

How does it scale to 100,000 users?

Keep the API stateless, send jobs to a queue, run autoscaled workers, store metadata in PostgreSQL and files in object storage, cache immutable rule sets, isolate document conversion, and use event streams or polling for status. LLM quotas and cost need per-user limits, retries with backoff and observability.

Advanced system-design prompt: “Design this module”

Use this repeatable answer order whenever someone names a module—journal discovery, compliance scoring, document editing, or billing.

StepWhat to say
1. Clarify goalWho uses it, expected volume, latency, correctness requirement, privacy boundary, and what “done” looks like.
2. State contractInputs, outputs, failure modes, idempotency key, permissions, and observability events.
3. Choose data modelIdentify entities, ownership, lifecycle, constraints and indexes before choosing a database.
4. Draw the hot pathClient → API → durable record → queue/worker → artifact → status/result.
5. Handle failureTimeouts, retries, duplicate delivery, partial output, cancellation, recovery and safe cleanup.
6. Explain trade-offWhat you optimize now, what you intentionally defer, and the trigger for the next architecture step.

Example: journal-rule discovery module

Contract

Input: journal name/URL. Output: normalized rule set with source URLs, extraction timestamp, confidence and validation errors. Only published/approved rules can be used by default.

Flow

Search/fetch → sanitize HTML/PDF → extract candidate rules → LLM structured extraction → schema validation → human review if confidence is low → versioned save.

Storage

PostgreSQL stores rule-set metadata and version status; object storage keeps source snapshots. Cache approved rules by journal + version.

Defenses

Respect source terms, protect SSRF with URL allowlists/network controls, record citations, never silently substitute unverified rules, and preserve the prior approved version.

Questions you should ask back

“What is the target concurrency?” “May users edit the result before applying it?” “How long may manuscript data be retained?” “Is exact citation conversion required, or is review acceptable?” “Which journal rules are authoritative when sources conflict?” These questions show that system design begins with constraints, not technologies.

Demo narrative

Use one sample paper. Upload it, select a target style, show the pre-check, explain the asynchronous status display, open the compliance report, preview a visible change, download the DOCX, and finally open the rule JSON/code path that explains why the change happened. This proves user value, system behavior and engineering accountability in one flow.
